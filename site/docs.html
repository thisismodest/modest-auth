Getting started

terminal
$ npm install modest-auth

Node 24 or later, and tested on 24 and 26. The first time node:sqlite is used, Node 24 prints a warning that SQLite is experimental: that's Node's own notice about its built-in module, not an error. In Node 26, node:sqlite is a release candidate (stability 1.2).

server.ts
import { createServer } from "node:http";
import { DatabaseSync } from "node:sqlite";
import { createAuth, createHandler, handleNode, toRequest } from "modest-auth";

// Its tables (auth_users, auth_sessions, auth_links, auth_limits) can live in your app's own database.
const auth = createAuth(new DatabaseSync("app.db"));
const handler = createHandler(auth, {
  origin: "https://example.org", // your site's address (HTTPS)
  linkPage: "/account/link", // your page that emailed links open
  sendEmail: (to, subject, text, { signal }) => sendWithYourService({ to, subject, text, signal }),
});

const server = createServer(async (req, res) => {
  if (await handleNode(handler, req, res)) return; // /auth/*, answered; anything else untouched
  const user = handler.userOf(toRequest(req)); // who's signed in, or null
  res.end(user ? `Hello, ${user.email}` : "Hello");
});
server.requestTimeout = 10_000; // slow clients get ten seconds, not five minutes
server.headersTimeout = 10_000;
server.listen(3000);

The routes

Every POST takes JSON, and must come from your site's own pages.

RouteBodyDoes
GET /auth/session{ user: { email } }, or { user: null }
POST /auth/send-password-link{ email }Emails a link to choose a password: to sign up, or for a forgotten one
POST /auth/send-sign-in-link{ email }Emails a link to sign in
POST /auth/link{ token }{ kind, email }: which email a link is for
POST /auth/set-password{ token, password }From a password link: makes the account or replaces its password, signs in, and ends every other session
POST /auth/sign-in-with-link{ token }From a sign-in link: signs in
POST /auth/sign-in{ email, password }Signs in, with a fresh session (any old one ends)
POST /auth/sign-outnoneEnds this session
POST /auth/sign-out-everywherenoneEnds every session of the account
GET /auth/sessionsThe account's sessions: { sessions: [{ id, started, lastUsed, current }] }
POST /auth/end-session{ id }Ends one of them
GET /auth/my-dataEverything kept about the account, as a file to save
POST /auth/password{ current, next }Changes the password, and ends every other session
POST /auth/change-email{ password, email }Signed in: emails a link to the new address
POST /auth/confirm-email{ token }From that link, signed in to the account: moves it, and ends every session
POST /auth/undo-email{ token }From the notice to the old address (for 7 days): moves it back, ends every session, and emails a link to choose a new password
POST /auth/delete-account{ password }Deletes the account and its sessions

The two that send a link answer 202 and {} whatever happens, so nobody can tell whether an email has an account; an email goes either way. Links last 60 minutes (password) or 15 (sign-in), and work once.

New passwords are 15 to 200 characters, any characters at all, but not a common password, not made from the email, and not with fewer than four different characters. A session lasts 30 days, or ends after 7 days unused.

From your pages

Send each route JSON with fetch, which another site's page can't do without the browser asking first. (A plain HTML form can't send JSON.)

sign-in.js
const res = await fetch("/auth/sign-in", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ email, password }),
});
if (!res.ok) showError((await res.json()).error.message); // fit to show as it is

The link page

Emailed links open your page at linkPage, with the token after #: /account/link#password=…, #sign-in=…, #email=…, or #undo=…. Browsers never send what follows # to a server, so the token stays out of logs, and a mail service that opens links to check them can't use one up. The page:

  1. Reads the token first, before any other script runs, and takes it out of the address bar. Keep analytics and other sites' scripts off it.
  2. Asks /auth/link which email it's for, and says so: "Choose a password for ann@example.org", or "Sign in as ann@example.org".
  3. Waits for the person to act. It never acts by itself: someone could send a person their own link, to sign them in to the wrong account. Showing the email is what lets them notice.
  4. Sends the token with the password to set-password, or alone to sign-in-with-link, confirm-email, or undo-email.
link.js
const [kind, token] = location.hash.slice(1).split("=");
history.replaceState(null, "", location.pathname);
const { email } = await post("/auth/link", { token });
show(kind === "password" ? `Choose a password for ${email}` : `Sign in as ${email}`);
// Then, only when the person presses the button:
await post(kind === "password" ? "/auth/set-password" : "/auth/sign-in-with-link", { token, password });

Your own routes

Ask who's signed in, and check that anything that changes something came from your own pages:

server.ts
const request = toRequest(req); // headers only: your own reading of the body is undisturbed
const user = handler.userOf(request); // { id, email }, or null
if (req.method === "POST" && !handler.fromSite(request)) return res.writeHead(403).end();

Link your own tables to accounts, so they go when an account is deleted:

schema.sql
CREATE TABLE notes (id INTEGER PRIMARY KEY, user TEXT REFERENCES auth_users(id) ON DELETE CASCADE, text TEXT);

Settings

Each is a fact about your site, not a choice of how secure to be.

origin

Your site's address, such as "https://example.org". HTTPS, except localhost for development. The cookie is worked out from it.

trustedProxies

Only with a CDN in front: its address ranges. Proxies on this machine or a private network (nginx, Caddy, a hosting platform's) are trusted without it, however many there are.

linkPage

Your page that emailed links open, such as "/account/link".

sendEmail

How your app sends email: (to, subject, text, { signal }). Pass the signal to fetch (it aborts after 30 seconds), and don't log the text: it holds the link.

onEvent (createAuth)

Optional: told of each sign-in, failure, pause, and change, after the answer, with the account's id and where it came from. Never a password, token, or email.

breachedRange (createAuth)

Optional: given a 5-character prefix of a password's SHA-1, gives Have I Been Pwned's range for it; breached passwords are refused.

base

Where the routes live. "/auth" unless you say otherwise.

What your app does

  • Serves the site over HTTPS.
  • Has a link page that shows which email a link is for, and acts only when the person does.
  • Lists a CDN in front, if there is one, as trustedProxies. Other proxies need nothing.
  • Checks its own changing routes with handler.fromSite(request).
  • Sets short timeouts for slow clients.
  • Keeps scripts out of its pages (a content security policy helps).
  • Keeps passwords out of its logs, and its proxy's.
  • Keeps the database on a local disk, backs it up, and keeps the backups private.
  • Watches for refusals: a run of 429 or 503 is someone guessing.
  • Leaves /auth to the handler: every path under it is the handler's.
  • Tells people who think their session was stolen to sign out everywhere first: it needs no password.

Other servers

handler.handle(request, remoteAddress) takes a Web-standard Request and gives a Response, or null for paths that aren't its own.

server.ts
// Bun
Bun.serve({ fetch: async (req, server) => (await handler.handle(req, server.requestIP(req)?.address)) ?? app(req) });

// Deno
Deno.serve(async (req, info) => (await handler.handle(req, info.remoteAddr.hostname)) ?? app(req));

// Express: first, before any body parser
app.use(async (req, res, next) => (await handleNode(handler, req, res)) || next());

Using the parts

createAuth gives the accounts, sessions, and limits without the routes. Your app then does what the handler would: checks Origin, starts a fresh session at each sign-in, passes where each request came from, and for links, sends the email requestLink gives after answering, whatever it says, and answers the same either way.

auth.Does
requestLink(kind, email, from)An email to send, or null: { kind, to, token, account, expires }, with token null when it should say there's no account
lookUpLink(token, from)Which email a link is for, without using it
usePasswordLink(token, password, from)The account, made or with its new password; every session ends
useSignInLink(token, from)The account a sign-in link is for
signIn(email, password, from)The account, if the password's right
startSession(user)A session token, for a user just returned by the calls above
userOf(token)Who a session belongs to, or null
endSession(token), endAllSessions(userId)Sign out, here or everywhere
sessionsOf(userId, token), endSessionOf(userId, id)The account's sessions, and ending one
dataOf(userId)Everything kept about the account
changePassword(userId, current, next, from)A new password; every session ends
requestEmailChange(userId, password, email, from)An email to send to the new address, or null
useEmailLink(token, userId, from)Moves the account signed in as userId; gives the previous email and an undo token for it
useUndoLink(token, from)Moves it back, and makes its password useless
deleteAccount(userId, password, from)The account and its sessions, gone

from is addressKey({ remoteAddress, forwardedFor }, trustedProxies); refuse a request whose address comes back "unknown". Cookies come from sessionCookie(token, origin), clearedCookie(origin), and readSessionCookie(header, origin).
