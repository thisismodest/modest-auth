Sign-in for Node.
Simple, and secure.

Email and password, sessions, and nothing you don't need. No dependencies, no settings that weaken it, and small enough to read in one sitting.

Early: not yet on npm, and not yet independently audited. Please don't use it for anything real yet.

  • 0dependencies
  • ~900lines of source
  • 7routes, ready-made
  • 1SQLite file

Getting started

Node 24 or later. Sign-up, sign-in, and sign-out for a whole site:

import { createServer } from "node:http";
import { DatabaseSync } from "node:sqlite";
import { createAuth, createHandler, handleNode, toRequest } from "modest-auth";

const auth = createAuth(new DatabaseSync("app.db"));
const handler = createHandler(auth, { origin: "https://example.org" });

createServer(async (req, res) => {
  if (await handleNode(handler, req, res)) return; // the /auth routes
  const user = handler.userOf(toRequest(req)); // who's signed in, or null
  res.end(user ? `Hello, ${user.email}` : "Hello");
}).listen(3000);

Your pages send JSON:

await fetch("/auth/sign-in", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ email, password }),
});

The docs have the rest: every route, the errors, and what your app does round it.

Simple

  • No dependencies. Only Node's own crypto and node:sqlite: nothing else to trust, update, or have compromised.
  • No settings that weaken it. The secure way is the only way.
  • The routes come ready-made, with the checks an app could forget built in.
  • About 900 lines, and a promise to stay under 1,000. Read all of it in an afternoon.

Secure

  • Passwords hashed with scrypt at OWASP's cost, and chosen by NIST's rules: 15 characters or more, and not one of 5,500 common ones.
  • Sessions in a cookie scripts can't read, kept only as hashes, ended when unused.
  • Guessing is slowed per account and per address, before any password is checked.
  • Other sites can't act for someone who's signed in.
  • Every promise has a test that fails if it stops being true.

Why so little?

Most authentication breaches aren't in the cryptography. They're logic bugs in features: two options that interact in a way nobody tested, or a flow added for one case that opens a door in another. The more an auth library does, and the more it can be configured, the more of those there are to find.

So modest-auth does the least that sign-in needs, the same way every time. If you need social sign-in, single sign-on, or passkeys today, use a larger library. If you need people to sign in with an email and a password, safely, this is for you.

Deliberately not here

Not hereWhy
JWTsA session in the database can be ended at once; a JWT lasts until it expires.
Plugins and hooksEvery extension point is a way to break the guarantees.
Other databasesSQLite is built into Node: one database is one thing to get right.
Social sign-in, single sign-onPerhaps later, one at a time, if they can be made as small and certain as the rest.
